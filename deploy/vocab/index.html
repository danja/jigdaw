JigDAW vocabulary

Namespace http://purl.org/stuff/jigdaw/, prefix jig:. Also available as Turtle, which is what you get if you ask for text/turtle.

Terms describing how an audio plugin is fetched and run in a web browser. What a plugin is musically comes from the transmissions vocabulary, which this one extends rather than replaces. Parameters are described with LV2.

This page is generated from the vocabulary, so it cannot drift from it. 80 terms.

Classes

jig:AutomationRate Automation Rate
No description.
jig:Capability
Something a host either offers or does not. A plugin names one with trn:requires when it cannot run without it, or jig:prefers when it can. Both are answered before any code is fetched, so an unsatisfiable plugin is reported rather than loaded and then found wanting.
jig:Connection
A directed link between two endpoints. Topology is modelled as explicit connections with named endpoints, never as a list, so the graph is a faithful picture of the dataflow rather than an encoding of one.
jig:Endpoint
One end of a connection: a node, and which of its ports.
jig:Inspection
A record of what a host observed when it actually loaded a module: the exports it found, the port counts it read back, the features it needed. This is the discovered half of the two-layer split JigDAW inherits from transmission. Inspection is authoritative for technical facts and the curated profile is authoritative for what the signals mean, because the two answer different questions and the second cannot be derived from the first.
jig:Module
The WebAssembly binary carrying the plugin's signal processing.
jig:ModuleAbi Module ABI
A published calling convention between a host and a WebAssembly module, letting a host without a JavaScript engine load the module directly.
jig:Node
One instance of a plugin in a project. Distinct from the plugin itself, because a project may hold several instances of one plugin, each with its own parameters and state.
jig:ParameterSetting Parameter Setting
A parameter's value on one node. Addressed by lv2:symbol rather than by index, because an index is a property of a build and a symbol is a property of the plugin.
jig:Processor
The JavaScript module passed to AudioWorklet.addModule. It calls registerProcessor and is the only plugin code that runs on the audio thread.
jig:Project
A session: nodes, connections, parameter settings and transport.
jig:Resource
A fetchable file belonging to a plugin. Its jig:location is resolved against the profile's own IRI, so a profile that moves keeps working and a plugin can be served from a directory copied anywhere.
jig:TempoPoint Tempo Point
A tempo, from a given beat onward. Ordered by jig:atBeat, not by position in a list.
jig:Transport
No description.
jig:UserInterface User Interface
The plugin's editor. It is a document loaded into a sandboxed frame, not a script loaded into the host's page, so a plugin cannot reach the host's DOM, its storage or its audio graph. A plugin with no jig:ui gets a generic panel generated from its declared lv2:port list, which is the expected case rather than a degraded one.
jig:WasmFeature WebAssembly Feature
A WebAssembly proposal the module's bytecode relies on. Declared because feature detection after instantiation is too late: an unsupported opcode fails at compile time with a message that names the byte offset and nothing else.
jig:WebPlugin Web Plugin
A plugin profile that additionally declares everything a browser needs to load and run the plugin. A subclass rather than a separate class so that an existing trn:PluginProfile becomes loadable by adding statements, never by being rewritten. A profile typing itself only trn:PluginProfile stays valid and stays findable; it is simply not installable here.

Object properties

jig:abi ABI
The calling convention this module implements, if any. Absent means the module is private to its processor, and only a browser can run the plugin.
jig:asset
Any further file the plugin needs, such as an impulse response or a wavetable. Listed so a host can prefetch, cache and integrity-check it, and so an offline or archived copy of a plugin is known to be complete.
jig:automationRate automation rate
Whether the parameter is sampled once per render quantum or once per frame, which is the AudioParamDescriptor automationRate. LV2 has no equivalent because its control ports are block-rate by construction. Default is k-rate: a parameter is a-rate only when it is meant to be audio-modulated, and making every parameter a-rate costs a Float32Array per parameter per quantum.

jig:integrity
A Subresource Integrity digest, as in sha384-<base64>. Required for every resource, because the profile and the code it points at need not come from the same origin and the whole install story is that a host runs code it found by following a link.
jig:latencyFrames latency frames
Frames of delay the plugin introduces, for the host to compensate.
jig:loadOutcome load outcome
What happened: loaded, refused, or failed, with the reason. A plugin that fails to load is a recorded result, not an error, so that a catalogue can report which plugins work in which browsers.

jig:mediaType media type
The media type the resource is expected to be served as. A statement of intent that lets a host report a misconfigured server precisely, rather than a substitute for the Content-Type header, which still governs.
jig:nodeState node state
The plugin's own saved state, opaque to the host. Parameter values are not state and do not belong here: they are settings, and storing them twice means the two disagree on restore with no defined winner.
jig:outputChannels output channels
Channels per output. A host declaring outputChannelCount on the node must agree with this, and a plugin writing a different number of channels is a load-time error rather than a silent half-signal.
jig:paramIndex parameter index
Which index this parameter has in jig_set_param. Required on every port of a module declaring an ABI, because a host loading the module directly has no processor to hold the mapping and cannot infer it: a position in the profile is a property of the document, not of the module.
jig:portIndex port index
Which audio input or output, zero-based, as Web Audio numbers them.
jig:portSymbol port symbol
The lv2:symbol of a parameter, when a connection targets one rather than an audio port. Modulating a parameter is an edge to a named thing, not to a numbered one.
jig:registeredName registered name
The name the processor module passes to registerProcessor. The host needs it to construct the AudioWorkletNode, and there is no way to ask a worklet what it registered.
jig:renderQuantum render quantum
Frames per process call the plugin is written for. Web Audio fixes this at 128 today. Declared rather than assumed because the figure is a specification constant that has been proposed for change, and a plugin that has baked 128 into a buffer size should say so rather than corrupt memory if it ever moves.
jig:revision
Increments on every committed change. A caller submitting a changeset names the revision it last saw and is rejected if the project has moved on. An agent and a person editing one project is the normal case here.

Individuals

jig:Abi1 JigDAW ABI 1
The first published ABI. Exports jig_init, jig_max_frames, jig_output_ptr, jig_process and jig_set_param, plus jig_input_ptr when the plugin takes audio and jig_note_on, jig_note_off and jig_all_notes_off when it takes MIDI. One pointer per channel; nothing is interleaved.
jig:Abi2 JigDAW ABI 2
Everything ABI 1 requires, plus three optional facilities it deliberately left out: MIDI arriving as whole frame stamped messages rather than note on and note off alone, MIDI leaving the module the same way, and a host transport carrying tempo, meter and bar, beat and tick. Each is declared by the profile and absent otherwise, so a module using none of them is an ABI 1 module under another name and a host that speaks ABI 2 speaks ABI 1. Added because a MIDI generator could not be written at all under version 1: it had nothing to emit through and no transport to be in time with.

jig:MidiEvents MIDI Events
The host delivers and accepts MIDI. The Web Audio graph carries no MIDI, so this is a host service over a message port rather than a property of the audio connection, and a plugin that produces trn:Midi must require it.
jig:MidiOut MIDI output
The host will collect MIDI the plugin emits and deliver it onward. A plugin that produces MIDI and does not ask for this has its output go nowhere, exactly as an incoming MIDI plugin does without jig:MidiEvents. Named separately because the two are separate services: a host may route MIDI to a plugin and have nowhere to send what comes back.
jig:OfflineRender Offline Render
The plugin may be run faster than real time in an OfflineAudioContext. A plugin whose output depends on wall-clock time, or on a device the offline context does not have, declares that it does not support this.
jig:Persistence
The host will save and restore the plugin's state with the project.
jig:SharedMemory Shared Memory
SharedArrayBuffer between the audio thread and elsewhere. Available only in a cross-origin isolated page, which in turn requires every cross-origin subresource to opt in with Cross-Origin-Resource-Policy. Requiring it therefore constrains not just the host but every server that hosts a plugin, which is why it is negotiated rather than assumed.
