The JigDAW plugin system

A plugin is a URL. Dereference it and it runs, in a browser, with no installation step distinct from having fetched it.

A native plugin has an identity, some metadata and a delivery mechanism, and they are three separate things: a class ID, a catalogue entry, an installer. JigDAW collapses them into one IRI. Ask that IRI for text/turtle and you get a description of what the plugin is, what signals it takes and produces, what it needs from a host, and where its WebAssembly lives. Fetch that, and it plays.

curl -H 'Accept: text/turtle' https://strandz.it/jigdaw/plugins/cascade/

How a plugin is described

A profile is RDF, written in three vocabularies. Which one a statement belongs to is not a detail: it is what lets the same description serve a browser, a native host and a catalogue without any of them agreeing in advance.

VocabularySaysExample
trn:What the plugin is, musically: its role, the signals it accepts and produces, what it pairs withtrn:role trn:AudioEffect
jig:What it takes to run it in a browser: the module, the processor, integrity digests, host capabilitiesjig:module <cascade.wasm>
lv2:Its parameters: symbols, ranges, units, scale pointslv2:minimum 0.0

The musical half is the transmissions vocabulary, shared with several native projects, so a JigDAW plugin is a valid entry in an existing catalogue rather than a new kind of thing. The parameters are plain LV2, which is why an LV2 plugin's port descriptions map in without translation. Only the middle row is ours, and it is published at http://purl.org/stuff/jigdaw/.

jig:WebPlugin is a subclass of trn:PluginProfile, not a replacement for it. An existing catalogue entry becomes loadable by adding statements, never by being rewritten, and a profile describing a native-only plugin stays valid. It is simply not installable in a browser.

What a plugin is made of

A profileRDF served at the plugin's own IRI. Identity, meaning and the links to everything else.
A processorA JavaScript module registering an AudioWorkletProcessor. The only plugin code on the audio thread.
A moduleWebAssembly doing the signal processing. Optional, but the point.
A user interfaceOptional. Without one, a host generates a panel from the declared parameters, which is the expected case rather than a degraded one.

Where this has got to

Honestly, because a specification that overstates itself is worse than none.

  • Works: loading a plugin from its IRI, profile validation, integrity verification, WebAssembly instantiation, generated panels, parameter automation, MIDI routed by the host, transport, latency compensation, cycle refusal, searching a catalogue, and an agent tool surface.
  • Exists but is thin: the DAW itself. There is a transport, a signal chain and a keyboard. There is no timeline, no recording and no mixer.
  • Not done: plugin user interfaces of their own. A host generates panels from declared parameters; the sandboxed frame protocol is specified and not implemented.

Worked examples

Two real plugins, both built from this repository and served by this host.

Cascade A Schroeder plate reverb. Audio in, audio out, five parameters including a freeze.
