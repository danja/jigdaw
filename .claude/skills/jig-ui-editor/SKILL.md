# Giving a plugin its own editor

A `jig:ui` is a web page the host loads into a sandboxed frame and talks to only by `postMessage`. It is for what a skin cannot draw. Read
[docs/plugin-ui.md](../../../docs/plugin-ui.md) for the bridge and [docs/host-plugin-contract.md](../../../docs/host-plugin-contract.md)
section 9 for the rules; this is the order of work.

## 1. Decide that it is an editor

- **Needs code** (a transfer curve, a spectrum, a plot with draggable nodes, a meter): an editor. Dynamix and Octet are editors.
- **Only controls and labels:** not an editor. Use an HTML skin (the `html-skin` skill), which the host draws with its own accessibility and
  needs no frame. A plugin whose controls fit a skin got no benefit from the frame (Canticle began as an editor and became a skin).
- **An editor is never the only way to anything.** The generated panel is always there and reaches every port, so everything an editor
  does must also be possible there (contract section 9.1). Do not put a port only on the editor.

## 2. The files and the build order

```
plugins/<name>/ui/src.html      what you write, with <script data-jig-bridge></script> where the bridge goes
plugins/<name>/ui/index.html    generated by bin/inline-ui.js: never edit it
```

In `profile.json`, under `resources`, add `"ui": "ui/index.html"`. In the plugin's `build.sh`, run the inliner **before** the profile
writer, which digests the result (see `plugins/dynamix/build.sh`):

```sh
node "$root/bin/inline-ui.js" "$here"
node "$root/bin/write-profile.js" "$here"
```

The page is one file with its script inline because the profile's `jig:integrity` digest covers one file, and a script fetched separately
would be code the digest does not cover. Run `bash plugins/<name>/build.sh` after every edit.

**Changing the bridge (`src/plugin-ui/JigUi.js`) or the unit text it shares (`src/ui/PortText.js`) makes every committed editor stale.**
`tests/bin/inline-ui.test.js` finds every plugin with a `ui/src.html` and fails if its `index.html` is not what the inliner now makes of it,
so rebuild each plugin that has one, then its digest.

## 3. The page

Bind controls with attributes and let the bridge do the messaging. The full list is in plugin-ui.md; the ones that matter:

```html
<input type="range" data-param="threshold">
<select data-param="comp_mode"></select>        <!-- options come from the port's scale points: write none -->
<label for="threshold" data-param-name="threshold"></label>
<output data-param-text="threshold"></output>   <!-- "-18 dB" -->
<p data-param-help></p>                          <!-- what the hovered or focused control does -->
```

For anything the attributes cannot say, the script is `jig`: `jig.ready` (a promise, resolved when the host has sent `init`),
`jig.on(symbol, fn(value, text))` (called now if known, then on every change the host applies), `jig.onPlugin(fn)` for data from the
processor, and `jig.begin/set/end/change` for a control the page draws itself, such as a node on a plot. Dynamix's
`plugins/dynamix/ui/src.html` is the worked example: it draws the curve from the threshold, ratio, knee, make-up and mode, and a dot at the
live level.

**Render from what the host says, never from the pointer.** A requested value may come back clamped, rejected or overridden by
automation, so a control moves only in the host's reply (messaging.md section 2.3). The bridge does this for bound controls; a control
you draw yourself must do it too: `jig.set` sends a request, and the picture changes in `jig.on`.

## 4. Data from the processor

The processor sends `{ type: 'plugin', payload }`, and the page receives `payload` in `jig.onPlugin`. Rules from the contract and from
Dynamix:

- **One object for the life of the processor, mutated and reposted**, so the audio path allocates nothing; only the structured clone copies.
- **Throttle it.** Dynamix posts every 16th quantum, about 23 a second at 48 kHz. The host's relay limit is `relayPerSecond` in
  `web/host.json` (60 when this was written), and above it the host throttles rather than letting a frame starve the page.
- Send **what the page draws from**, numbers and not markup. The payload is data and is never inserted as markup or run: use `textContent`.
- **Cap what you show.** An expander on silence is attenuating by hundreds of dB, which is true and unreadable: Dynamix prints
  "over 60 dB" and puts the dot away.
- If the numbers come from the module, export them as **optional** read-only functions (`jig_gain_reduction_db`), written once per block
  and never read by the audio path, and have the processor send them only if the module exports them.

## 5. Accessibility, which the frame does not give you for free

- A decorative curve or meter is `aria-hidden`, and its facts are also **text**: "Gain reduction 6.0 dB". Do not make a fast display a live
  region: twenty updates a second drown everything else a screen reader says.
- Everything a pointer does on a plot, the keyboard does too (Octet's header says so, and it is a requirement). A visible focus indicator;
  targets of at least 44px; text inputs at 16px or more, or iOS zooms; one column on a phone.
- Do not signal state by colour alone.

## 6. What the sandbox means

The frame has `sandbox` with `allow-scripts` and `allow-same-origin` and nothing else, so every message can be addressed to its real origin:
`"*"` is allowed only for the first `ready`, which carries nothing. The page gets the profile and the values and nothing else: no
`AudioContext`, no node, no project. It cannot touch the network or storage. Where the host serves the plugin itself the frame is
**same-origin**, which is a document boundary and not a security boundary: do not describe it as isolated. The bridge handles all of this;
a page that sends its own messages must too.

## 7. Test it

Model `tests/ui/dynamix-ui.test.js`. A page is tested in Node against linkedom: evaluate its inline scripts in a function given `document`,
`window` and `parent`, deliver an `init` made from the **real** profile (`profileAsJsonLd`), and assert.

- **Every port is reachable** from the editor, and only real ports are bound.
- **Deliver a message, then wait one tick.** The page registers its listeners inside `jig.ready.then`, which runs a microtask after `init`.
- **Hold a drawn law to the module.** Give the same settings to the wasm and to the page's function and require the levels to agree
  (Dynamix's curve is held to within 0.3 dB). A curve that draws a law the processor does not apply is worse than none.
- Cases that are easy to forget: a payload that is not numbers, silence, the stage switched off, and a hostile string where text is shown.
- linkedom has no layout and a `select` with no settable `value` (set `option.selected`); it cannot test dragging. `tests/plugin-ui/` holds
  the bridge's own tests; you do not repeat them, you test your page.

## 8. Look at it in a real browser

Use the `browser-check` skill. In the Plugins tab, a plugin with an editor has an **Open editor** button; the editor appears in a section
labelled "<name> editor" holding an `iframe`. Same-origin, so `iframe.contentDocument` works and you can read and drive it. Count: a real
drag across a slider, five key presses, and a change that you see come back from the host. **Wait about half a second before reading what
came back:** the frame hears from the host by `postMessage`, which is asynchronous, so a read straight after the key presses shows the old
readout and the old curve and looks exactly like a broken round trip. (Found by following this skill on Dynamix: five presses on Ratio
moved the slider by exactly 0.475, the readout still said 4.00, and 800 ms later it said 4.51 and the host's own panel agreed.) Check the
host's generated panel behind the editor too: it is the model's own view of the value. Look for what the unit tests cannot: layout at
several widths, the focus ring, a meter that moves while the plugin plays (which needs the window in front and audio started by a real
click, and which you cannot hear: say so).

## 9. Done when

`build.sh` ran after the last change and the editor's `index.html` is current; every port is also on the generated panel; the page test
passes and any law it draws is held to the module; the editor has been seen in Chrome with the checks counted; the `finish-plugin`
list is done; and you have said what was not checked (sound, touch, a screen reader).
